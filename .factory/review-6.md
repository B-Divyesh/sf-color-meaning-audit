# Adversarial first-read review 6 — Signal Check

**Reviewed:** 2026-08-28  
**Live URL:** <https://color-meaning-audit.sociobot.in/>  
**Review checkout:** fresh shallow clone of `main` at `27ae881ddd5ed4de4ac7d5a40c270632e3a8bef9`  
**Viewports:** fresh Chromium contexts at 390×844 and 1440×900  
**Verdict: FAIL**

The product is clear and tryable at first read. The registered product claims all passed their exact commands. It nevertheless fails the factory contract because a new clean clone cannot run the required quality gate reproducibly: `npm ci` has no lockfile to use, and a normal install makes `npm test` fail at TypeScript typecheck. Two smaller remaining issues are recorded below.

## Cold first read

Before scrolling, at both 390 px and desktop, I understood:

- **What it does:** checks charts and status dashboards for meaning carried only by color, then asks me to use another cue.
- **For whom:** people with color-vision differences who need to act on the information.
- **What to click first:** **“Try sample data — see a color-only warning.”**

The evidence is all in the first screen: “Check color-only signals before you act.” and “For people with color-vision differences who need to act, check charts and dashboards for meaning carried only by color.” The primary link is direct and names its result. There was no console error, storage, cookie, or horizontal overflow in either fresh context. This mandatory first-read check passes.

## Findings, ordered by severity

### F-6-1 — BLOCKING: a clean clone cannot run the required quality gate reproducibly

**Location:** repository root; `package.json` has no accompanying `package-lock.json`.

**Evidence:** From a fresh shallow clone, `npm ci` exits with `EUSAGE`: “The `npm ci` command can only install with an existing package-lock.json or npm-shrinkwrap.json.” As a diagnostic fallback, `npm install --no-package-lock` installed 260 packages, but resolved two incompatible `playwright-core` versions: `@playwright/test@1.58.2` uses `1.58.2`, while `@axe-core/playwright@4.10.2` resolved `1.62.1`. `npm test` then fails before tests run with TS2740 in `tests/e2e/overlay.spec.ts:27`, `popup.spec.ts:159`, and `site.spec.ts:126`; the reported `Page` type lacks methods such as `ariaSnapshot`.

**Why this fails:** The product contract requires a passing local `npm test`. A contributor or factory worker starting from the published source cannot perform that check reliably. The claim commands happen to omit typecheck, so their passing results do not repair the failed quality gate.

**Concrete fix:** commit a lockfile produced with the supported npm version and pin/override the Playwright dependency graph so `@axe-core/playwright` and `@playwright/test` use compatible `playwright-core` types. In a newly cloned directory, require `npm ci && npm test` in CI. The test must complete without a fallback install or source edits.

### F-6-2 — P1: the landing footer makes an unlisted origin claim about the artwork

**Quote/location:** landing footer: “Built by Param Factory · build 1.0.5 · **hero artwork is original project artwork.**”

**Evidence:** The statement is present on the live landing page and in `site/index.html`, but `.factory/claims.json` contains no `original-artwork` entry or observable test. The registry covers download, demo behavior, local checks, views, and storage; it does not cover artwork origin.

**Why this matters:** This is a visitor-facing claim about the origin and licensing status of the visual asset. It cannot be established from the visitor-visible product through the claim-test contract, so the footer asks for trust beyond the registered evidence.

**Concrete fix:** remove “hero artwork is original project artwork” from the public footer and retain the provenance record in `.factory/design.md`. If the claim must remain public, add a narrowly scoped provenance manifest and a claim test that verifies the shipped asset is the manifest’s declared project asset; do not present that mechanical check as proof of creative originality.

### F-6-3 — P2: the offline demo is a second, incomplete route shell

**Location:** offline `/demo/` response generated by `site/sw.template.js` (`OFFLINE_DEMO`).

**Evidence:** After first visiting `/demo/?demo=1`, controlling the service worker, and reloading offline, the demo warning and boundary text appear, but the served document has no `<header>`, skip link, footer, Privacy/Terms links, favicon, canonical, Open Graph metadata, or route-focus handling. The source emits `<aside class="banner">` and `<main>` directly. This differs from the online `/demo/` document, whose `.demo-banner`, header, and footer satisfy the normal site shell. The offline fallback's “Locate these signals” control is also disabled without an explanation.

**Why this matters:** “Sample warning reloads offline after its first visit” sends a visitor into this document. The offline state is therefore part of the demo route, not an implementation detail. It loses the consistent navigation and legal routes promised by the site structure, and a keyboard user cannot tell why the visible Locate control cannot be used.

**Concrete fix:** serve the cached built demo shell and assets offline, or make `OFFLINE_DEMO` use the same header, skip link, footer, metadata, focused heading, and enabled/minimized overlay behavior. Add an offline route-shell test that asserts header/footer links, focus, and an explicit disabled-control explanation after the offline reload.
